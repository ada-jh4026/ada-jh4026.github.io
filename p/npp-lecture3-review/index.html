NPP Lecture 3 Review: Debugging

Topics: exceptions & tracebacks · avoiding bugs · static analysis · minimum failing examples · manual debugging · the pdb debugger · AI-assisted debugging

1. Why debugging matters

  • Developers often spend as much (or more) time debugging as writing "real" code.
  • Debugging is a skill you must actively develop to stay productive.

Famous bugs in history

Event Notes
The first "bug" (1947) Grace Hopper logged an actual moth stuck in a relay, popularising the term "debugging"
Y2K Two-digit years caused the year-2000 problem; billions spent fixing it worldwide
Dhahran missile (1991) A Patriot system clock drifted ⅓ s over 100 h, causing a failed intercept that killed 28 US soldiers

Fun bug types

Type Characteristic
Heisenbug Disappears or changes when you try to observe/debug it (quantum "observer effect")
Bohrbug Reproduces reliably under well-defined (possibly unknown) conditions
Mandelbug So complex it's practically unfixable (after Mandelbrot)
Schroedinbug Only manifests once you realise it "shouldn't work at all"

2. Python tracebacks and exceptions

Reading a traceback

A traceback is the call-stack report produced when an exception is raised. Read it bottom-to-top (the last line is where the exception fired, not necessarily the bug's root cause).

NameError: name 'exp' is not defined
  • The first line is the exception type; below Traceback (most recent call last) each call is listed.

Common exceptions (be able to trigger each)

Exception How to trigger
ImportError from numpy import alalalala
ModuleNotFoundError import what
ZeroDivisionError 1 / 0
IndexError [1,2,3][100]
TypeError "hello" + None
SyntaxError syntax errors (e.g. 2+2 =="4")
IndentationError missing indentation under for
RecursionError def f(): return f()

You can define custom exceptions; see the Python docs.

3. Avoiding bugs (write with debugging in mind)

  • Everyone writes buggy code — write it to be testable and debuggable.
  • KISS (Keep It Simple, Stupid): what's the simplest thing that could work?
  • DRY (Don't Repeat Yourself): each piece of knowledge has a single authoritative representation.
  • Loose coupling: limit interdependencies between parts of the code.
  • Meaningful names: name variables/functions/modules clearly, not cryptically.

4. Static analysis

  • Interpreted (Python/Matlab/JS) vs compiled (C/C++/Fortran): compiled languages catch some bugs at compile time; Python misses that step.
  • Python static-analysis tools:
    • pyflakes: simplest and fast; catches syntax errors, missing imports, name typos.
    • flake8: pyflakes + pep8, also flags PEP8 style violations.
    • pylint, pychecker; notebook version flake8-nb.
  • Integrate into your editor/IDE for big productivity gains.

5. The debugging workflow

No silver bullet, but a strategy helps. Ideal: isolate the bug to a few lines with a short modify-run-fail cycle.

  1. Make it fail reliably — find a test case that fails the same way every time.
  2. Divide and conquer — isolate the module → function → line.
  3. Isolate a minimum failing example (MFE).
  4. Change one thing at a time, re-run the failing case.
  5. Use the debugger to understand what's wrong.
  6. Take notes and be patient.
  7. After fixing, add the case to your test suite to prevent regression.

6. Minimum failing example (MFE)

  • The simplest code that reproduces a bug.
  • Providing an MFE is good practice when asking for help — it drastically cuts debugging time.
  • Open-source maintainers often reply "please provide an MFE".
  • Example: hundreds of lines of Devito code condensed to ~15 lines, then fixed in under an hour.

7. Manual debugging

  • print statements: print values near the suspected line to localise the bug.
x = some_function(inputs)
print(x.property1, x.property2)
  • IPython.embed(): drop into an interactive interpreter mid-code to inspect state.
x = some_function(inputs)
from IPython import embed; embed()

8. The Python debugger (pdb)

What it can do

  • View source; walk up/down the call stack; inspect/modify variable values; set breakpoints.

Three ways to launch

  1. Postmortem (IPython only): after an error, run %debug.
  2. Command line: python -m pdb script.py.
  3. In code: insert breakpoint() where you want to drop in (older equivalent: import pdb; pdb.set_trace()).

Common commands

Command Description
l(list) list code around the current position
p(print) print a variable (p a)
n(ext) next line (doesn't step into functions)
s(tep) next statement (steps into functions)
c(ontinue) continue to the next breakpoint
b(reak) set a breakpoint (b 34)
u(p) / d(own) move up/down the call stack
bt print the call stack
a print local variables
!command run a Python command (vs a pdb command)
q quit
h / help help

Turning warnings into exceptions

np.seterr(all='raise')   # make divide/invalid/over raise, enabling post-mortem debugging

Debugging in pytest

  • pytest --pdb my_test.py: post-mortem on exceptions.
  • pytest --pdb-failure: inspect test failures with the debugger.

GUI/alternative tools

  • pudb (semi-graphical console debugger), VS Code's debug mode, the Mu editor.

9. AI and debugging

  • AI (Copilot, Claude, …) is a powerful assistant but has limits: it can be misled, hallucinate, and write its own bugs.
  • Experience-based tips:
    • Some of the hardest-to-find bugs come from AI-generated code checked too hastily.
    • You are ultimately responsible for all the code you produce.
    • Context matters: chat UIs suit small snippets; agentic tools (Claude Code/Codex) suit large codebases but are often not permitted for assessed work.
  • Learning advice: you must be able to write code from scratch yourself; AI helps with learning (clarifying concepts, suggesting efficient approaches) but relying on it to write/debug code won't benefit you long-term.

10. Summary

  • Everyone writes bugs.
  • Debugging tools save time and energy.
  • Static analysis avoids many simple bugs.
  • Use IPython.embed() for manual debugging.
  • Learn the basics of pdb.
